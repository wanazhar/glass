# Pull request draft: Enforce lifecycle, recovery, and ownership invariants

**Status:** Pull request preparation. The 46 reproduced findings below were
addressed in separate commits, and the additional frontend race was fixed in
`be431605`. This is a targeted audit, not an exhaustive inventory. The paths
and line numbers in the findings describe the pre-fix checkout and may no
longer identify the corresponding code in the current tree.

## Pull request summary

This change set hardens durable task and conversation state, resident-agent
recovery, daemon shutdown and event cursors, debugger lifecycle, browser
transport ownership, and the Python, TypeScript, and Rust client protocols.
It also fixes cross-conversation frontend event handling, archive access,
native host-view performance, and TUI recovery and navigation. Follow-on
commits update browser and terminal smoke coverage and native test execution.

The findings record the observed failures and the intended invariant; they
are historical reproductions, not claims that the current code still has
those defects. The branch includes additional verification and user-interface
fixes beyond the original 46.

## Problem addressed

Several asynchronous and durable lifecycles allowed invalid combinations of
state, lost the identity of in-flight work, or reported success before the
relevant remote transition was confirmed. These failures could lose accepted
work, prevent recovery, leak sessions, and cause concurrent client operations
to fail.

## Reproduced findings

### Durable runtime and resident agents

1. **Recovery fails with more than 512 running tasks.** `crates/glass-core/src/durable.rs:771-780,830-848`: recovery collects every running task into one commit, while a commit permits at most 512 operations. Created 513 running tasks through `durable/commit`, restarted the runtime, and observed `commit requires 1..512 operations` when durable state opened. Recover in bounded, dependency-aware batches.
2. **Unavailable agent dependencies never settle.** `crates/glass-dev/src/agents.rs:343-388,1797-1839,2818-2844`: an interrupted, never-initialized run rehydrates as `Unavailable`; dependency validation accepts it, but failure propagation only handles `Failed` and `Cancelled`. In a temporary project with such a prior run, a dependent agent remained `queued` after refresh. Reject or explicitly propagate unavailable dependencies.

### Development daemon and debugger

3. **Idempotency does not bind an ID to its request.** `crates/glass-dev/src/daemon.rs:221-235,1017-1049`: the registry indexes only by request ID, not actor, tool, arguments, or execution context. Against a temporary daemon, submitting `glass.file.list` with the ID of a prior `glass.file.read` returned `accepted: true`, `created: false` and the read operation instead of reporting a mismatch. Store and compare a canonical request identity.
4. **A closing workspace accepts work it cannot settle.** `crates/glass-dev/src/daemon.rs:1129-1150,1324-1329,1458-1483`: while a running operation delays shutdown, a later `operation.submit` can be accepted after the shutdown command has cleared the queue. Reproduced with a two-second operation: the late read was accepted as queued, then workspace removal made it uninspectable. Reject admission once closing begins or settle every accepted operation before removal.
5. **A debugger launch timeout loses the outstanding request.** `crates/glass-dev/src/debugger.rs:614-637`: `configuration_done` removes `pending_start` before awaiting the launch response. With a temporary DAP adapter that did not answer launch, configuration timed out and a second launch was accepted. Retain the pending request or transition to an explicit indeterminate state until reconciled.

### Browser transport and remote sessions

6. **BiDi initialization leaks a partially created session.** `crates/glass-browser/src/browser/bidi_backend.rs:332-372`: after `session.new` succeeds, a failed/empty context lookup leaves `initialized` false; `close` rejects and retry sends another `session.new`. Reproduced with a local BiDi endpoint returning no contexts. Preserve the remote identity and clean up or expose a recoverable partial state.
7. **WebDriver initialization leaks a partially created session.** `crates/glass-browser/src/browser/webdriver_backend.rs:215-259`: the session ID is not retained until after window and URL discovery. An empty handle list made initialization fail, made `close` reject, and caused retry to create a second session. Retain and clean up the session on every later failure.
8. **WebDriver forgets a session after failed close.** `crates/glass-browser/src/browser/webdriver_backend.rs:257-269`: a failed session DELETE still clears the ID. A local fake driver returned HTTP 500; the second close reported already closed and did not retry DELETE. Preserve a close-failed/indeterminate state until remote termination is confirmed.
9. **BiDi close reports success after `session.end` fails.** `crates/glass-browser/src/browser/bidi_backend.rs:363-372`: the result of `session.end` is ignored. A fake endpoint rejected it and `Close` returned `Ok(Unit)`. Report unconfirmed remote termination separately from local socket closure.
10. **Dropping the last CDP client leaves its actor/socket alive.** `crates/glass-browser/src/browser/cdp.rs:377-390,393-420,1421-1424`: the actor keeps a strong sender to its own command channel, so dropping external handles cannot close the receiver. A local WebSocket probe observed the socket remain open after the last `CdpClient` was dropped while the runtime remained alive. Remove the self-ownership or implement last-owner shutdown.

### SDK client lifecycle

11. **Concurrent TypeScript initialization sends duplicate handshakes.** `clients/typescript/src/index.ts:552-568`; the server accepts initialization only once (`crates/glass-browser/src/mcp/server.rs:959-974`). Two simultaneous `listTools()` calls against Glass produced one success and one `initialize may only be requested once` error. Share the in-flight initialization promise.
12. **TypeScript requests after close write to an ended stream.** `clients/typescript/src/index.ts:1091-1107`: `close()` does not establish a terminal state checked by `request()`. Calling `listTools()` after close produced an uncaught `ERR_STREAM_WRITE_AFTER_END`. Reject new work after close or transport failure.
13. **TypeScript frame limits are applied to socket batches rather than individual frames.** `clients/typescript/src/index.ts:1110-1117`: two valid 97-byte responses delivered in one chunk with a 120-byte per-frame limit rejected both requests. Parse complete frames before enforcing the limit on each frame or incomplete remainder.
14. **Overlapping TypeScript lease scopes can release each other's authority.** `clients/typescript/src/index.ts:765-772`: a second scope borrows a present token, while the first releases it upon returning. A controlled client probe observed the second operation continue after the first had released the lease. Serialize scopes or retain the lease until all borrowers finish.
15. **Expired lease tokens are treated as held.** `clients/typescript/src/index.ts:614-632,765-772` and `clients/python/glass_client.py:556-583,745-753`: scope helpers test token presence, not validity. Against a temporary browser daemon, a 100 ms lease expired and a later TypeScript lease scope failed with `mutation lease has expired` rather than acquiring a usable lease. Track invalid/expired leases and define safe renewal or reacquisition.
16. **Python concurrent callers can consume and discard each other's replies.** `clients/python/glass_client.py:1194-1205`: each caller reads the shared stream and skips nonmatching IDs. Two concurrent calls with valid reverse-order responses resulted in one completion and one timeout. Serialize requests or implement response routing. The README does not currently state a thread-safety contract.
17. **TypeScript failed sends leave pending entries behind.** `clients/typescript/src/index.ts:1098-1107`: `pending` is populated before JSON serialization. Three calls with circular arguments rejected but left three pending entries. Serialize before insertion or remove entries when sending fails.

### Additional findings

18. **Failed durable creation and forks leave orphan projection files.** `crates/glass-core/src/durable_runtime.rs:192-216,219-270`: a projection session is created before the authoritative durable commit or all fork checks succeed, without cleanup on error. Against isolated runtime storage, `durable/create` with an unknown owner returned an error but left a projection JSONL; a fork at a boundary before an `as_of` document existed likewise failed and left a JSONL and writer lock. Ensure failed creation does not leave a discoverable orphan, or explicitly track and clean uncommitted projections.
19. **Raw commits bypass the idle-only reset guard.** `crates/glass-core/src/durable_runtime.rs:330-337,443-457`; `crates/glass-core/src/durable.rs:367-385`: `durable/reset` rejects a conversation with unfinished tasks, but `durable/commit` accepts `conversation.reset` while a task is running. Reproduced both requests against the same temporary runtime: the guarded reset failed and the raw reset succeeded at the next sequence while the task stayed `running`. Enforce the invariant in the authoritative operation application path, including multi-operation commits.
20. **Raw commits can persist invalid conversation metadata that crashes the runtime.** `crates/glass-core/src/durable.rs:357-365`; `crates/glass-core/src/durable_runtime.rs:273-290,330-337`: `conversation.configure` accepts any JSON value, but the higher-level configure path assumes an object and indexes it. Created a valid conversation, committed an agent value of `"not-an-object"`, then called `durable/configure` with a model patch; the runtime aborted with `cannot access key "model" in JSON string` (exit `-6`). Validate durable conversation metadata at the commit boundary and handle existing invalid records without panicking.
21. **Raw task updates bypass per-conversation generation ordering.** `crates/glass-core/src/durable_runtime.rs:142-167,330-337`; `crates/glass-core/src/durable.rs:478-512`: the scheduler's eligibility check excludes overlapping `gc.generation` tasks in one conversation, but the lower-level commit path permits each pending task to become `running` without that check. Created two generation tasks for one conversation, set both to `running` in one accepted commit, and observed both running in durable state. Enforce the same ordering invariant at the authoritative transition boundary. The reproduction establishes contradictory durable state; it did not execute two provider turns.
22. **Document forks can label an old value with a newer schema version.** `crates/glass-core/src/durable_runtime.rs:219-267`; `crates/glass-core/src/durable.rs:578-595`: for `fork: "as_of"`, the value comes from the historical snapshot but the version and definition come from the current document. For `fork: "initial"`, migration updates the version and current value but leaves the old initial value. In isolated runtime probes, both policies produced version-2 forked documents containing version-1-shaped values after migration. Copy a consistent historical definition and value, or explicitly migrate the selected value before marking it current.
23. **A waiting task can be made claimable while its dependency is unfinished.** `crates/glass-core/src/durable.rs:478-525,537-541,670-690`; `crates/glass-core/src/durable_runtime.rs:142-167,540-551`: reconciliation normally returns a waiting task to pending after its dependencies settle, but `task.update` also accepts `waiting` to `pending` and replaces `on` with an empty default. In a temporary runtime, a waiting task could not be claimed; after that update it was claimed and marked running while its dependency was still pending. If cancelling a wait is supported, make it an explicit operation; otherwise reject premature transitions.
24. **The Rust runtime client accepts a final frame without its newline delimiter.** `crates/glass-runtime-client/src/lib.rs:118-143`; `products/glass-core/docs/reference/runtime.md:68-69`: the protocol requires each JSON object to end with a newline, but `read_frame` parses nonempty EOF data without checking for that delimiter. A child process emitted a valid response object without a newline and exited; `recv_timeout` returned `Ok(Some(...))` instead of an incomplete-frame error. Reject unterminated EOF frames so a truncated stream cannot be mistaken for a complete protocol message.
25. **The Rust runtime client classifies an uncorrelated tool notification as an executable request.** `crates/glass-runtime-client/src/protocol.rs:147-157`; `products/glass-core/docs/reference/runtime.md:68-70,233-241`: `Incoming::parse` accepts `tool/execute` without an `id` and returns `Incoming::Tool { request_id: null, ... }`, even though the protocol requires tool request IDs and responses must echo them. A direct parser probe reproduced that classification. Require a valid request ID before handing a tool request to host execution; the probe did not execute a tool.
26. **A completing task can acquire new owned children.** `crates/glass-core/src/durable.rs:428-453,492-496,530-547`: after a parent decides its outcome, it enters `completing` while existing foreground children settle, and further parent updates are rejected. However, task creation only rejects terminal or aborting owners. In an isolated runtime, a parent entered `completing` with one child, then creation of a second child owned by that parent succeeded. Reject new owned work after completion is decided, or explicitly define and bound this transition.
27. **A lease-release error hides the operation's original error.** `clients/typescript/src/index.ts:628-632,765-772`; the Python helper has the same `finally` pattern at `clients/python/glass_client.py:577-583,745-753`. Against a temporary browser daemon, one TypeScript lease scope expired, another client acquired the lease, and the operation then failed with `original operation failure`. The caller instead received `mutation lease is held by another owner` from cleanup. Preserve the primary operation error while separately reporting the release failure; ensure local lease state is reconciled. The Python case is source-confirmed but was not separately exercised.
28. **Stopping a debugger can block on its transport reader after the adapter exits.** `crates/glass-dev/src/debugger.rs:196-219,221-258,261-277,515-547`: shutdown joins the reader and output-drain threads without ensuring their streams can reach EOF. In one local probe, a separate TCP peer kept the connection open after answering `disconnect`; `glass.debug.stop` blocked until that socket closed. In another, a stdio adapter's descendant inherited its pipes; stop blocked until the descendant exited. Shut down owned TCP connections, account for descendants holding stdio pipes, and bound the join without silently claiming cleanup succeeded.
29. **Recursive background cancellation stops at a completed intermediate task.** `crates/glass-core/src/durable.rs:251-267`; `products/glass-core/docs/reference/durable.md:75-82`: cancellation traverses only nonterminal direct children, even with `includeBackground: true`. In an isolated runtime, a root owned a background child, which owned a background grandchild. After the child completed, aborting the root with `includeBackground: true` left the grandchild pending with `abortRequested: false`. Define whether completed ownership nodes retain their descendants; if recursive cancellation includes them, traverse through terminal intermediates without changing their completed state.
30. **Unfinished-tool recovery has a separate 512-operation failure.** `crates/glass-core/src/durable_runtime.rs:69-96,134-135`; `crates/glass-core/src/durable.rs:771-780`: after task recovery, host startup collects every unanswered tool call into one commit, which also exceeds the 512-operation limit. In isolated storage, 513 unfinished tool-call records and no running tasks caused durable access after restart to fail with `commit requires 1..512 operations`. This is separate from finding 1's running-task recovery path; both recovery phases need bounded commits that remain correct if interrupted.
31. **An earlier tool result can hide a later unfinished call with the same provider call ID.** `crates/glass-core/src/durable_runtime.rs:77-96`; `crates/glass-core/src/session.rs:747-765`; `products/glass-core/docs/reference/runtime.md:217-218,393-395`: both durable and ordinary session recovery gather completed IDs across the whole conversation, without pairing each call with its corresponding later result. In separate isolated probes for both paths, a completed call ID was reused in a later turn without a result; recovery wrote an interrupted result for a separate unique unfinished ID but none for the reused ID. Match call/result occurrences in transcript order or use a durable per-occurrence identity; do not assume provider call IDs are globally unique across a conversation.
32. **A prior assistant message can suppress recovery of a distinct partial response.** `crates/glass-core/src/durable_runtime.rs:98-130`: recovery considers the current `gc.live` text already recorded if any assistant message since the last user message contains that text, without matching the response occurrence. In isolated durable storage, two conversations each had an earlier assistant message followed by a completed tool call and then a new partial response. The earlier message in one contained the new partial text; after restart, recovery appended the partial response only for the other conversation. The first partial remained in `gc.live` but was not added as a recovered transcript entry. Track the response occurrence or journal position rather than using substring equality.
33. **A completed shell command can be reported as interrupted after a crash.** `crates/glass-core/src/agent.rs:3131-3148,3594-3611`; `crates/glass-core/src/session.rs:747-765`: the completed `Bash` record and corresponding `ToolResult` are appended separately, and recovery recognizes only `ToolResult`. In an isolated ordinary session, a call followed by a recorded shell result with exit code 0 but no later tool-result record resumed with a synthesized message saying the command was killed and may have partially run. Commit the related records together or reconstruct the tool result from the completed shell record when its identity and outcome are sufficient.
34. **Recovery of bounded partial responses can exceed the commit byte limit.** `crates/glass-core/src/durable_runtime.rs:98-135,725-730`; `crates/glass-core/src/durable.rs:800-803`: startup combines all recovered partial responses in one commit. Even when each saved partial is within its 64 KiB bound and the operation count is below 512, the combined commit can exceed 1 MiB. In isolated storage, 18 conversations with 60,000-byte partials caused durable access after restart to fail with `durable commit exceeds 1 MiB`. Bound recovery batches by encoded byte size as well as operation count, and preserve recovery correctness across interrupted batches.
35. **Reusing a provider tool-call ID in a later round of one durable turn fails the turn.** `crates/glass-core/src/durable_runtime.rs:30-35,806-839`; `crates/glass-core/src/durable.rs:439-446`: the durable tool-task ID is derived only from the generation task and provider call ID, so a later distinct call with the same provider ID collides with the completed task. With a local mock provider returning `same-call-id` in two successive tool rounds, the first host call completed and the second failed before dispatch with `invalid or duplicate task definition`. Use a durable per-call-occurrence identity while preserving the provider ID for the protocol.
36. **Durable tool status is inferred from output text instead of the actual outcome.** `crates/glass-core/src/durable_runtime.rs:841-851`; `crates/glass-core/src/runtime.rs:1045-1052`: the durable observer classifies a tool as failed when its output begins with `error:`, even if the host explicitly reports success. With a local mock provider and a host result of `{"text":"error: this is successful content","isError":false}`, the runtime emitted `executionStatus: "completed"` while durable inspection showed the corresponding `gc.tool` task as `failed` with `isError: true`. Persist and use the typed outcome rather than parsing the body text.
37. **Explicit waits can deadlock against implicit foreground ownership.** `crates/glass-core/src/durable.rs:251-255,286-296,513-525,530-547,660-690`: cycle detection follows explicit `on` dependencies but not the implicit dependency from a completing parent to its active foreground children. In isolated runtime storage, a foreground child successfully entered `waiting` on its parent; completing the parent was accepted, leaving the parent `completing` and the child `waiting`. Reject cycles across both dependency types or otherwise ensure the parent can settle without the child.
38. **The unpaginated task graph becomes unreadable within supported state limits.** `crates/glass-core/src/durable.rs:985-986`; `crates/glass-core/src/durable_runtime.rs:460`; `crates/glass-core/src/runtime.rs:257-260`: `durable/taskGraph` returns every live task in one response, including checkpoints, without a page or size parameter. In isolated storage, 150 live tasks with 7,500-byte checkpoints were accepted in two commits; `durable/taskGraph` with `limit: 1` returned `response exceeds 1 MiB; request a smaller page`, while `durable/inspect` could still page the state. Provide a bounded graph representation or pagination that can reconstruct the graph.
39. **An accepted transcript entry can block transcript pagination.** `crates/glass-core/src/durable.rs:367-385,771-803,852-870`; `crates/glass-core/src/durable_runtime.rs:300-328`: the commit limit permits an inline entry larger than the 768 KiB entry-page limit. An 800,000-byte user record was accepted in isolated storage, but `durable/entries` at its cursor returned `entry exceeds response limit; use artifact range reads`; `durable/changes` at the preceding sequence returned a reset rather than the commit. The entry was inline, not an artifact reference. Enforce a compatible entry limit or provide a bounded way to read or skip oversized inline entries without losing transcript data.
40. **A task's terminal outcome changes shape depending on child timing.** `crates/glass-core/src/durable.rs:530-547,660-669`: a directly completed task stores its supplied outcome, while a task that first enters `completing` wraps that outcome as `{"status": ..., "result": ...}` and reconciliation leaves the wrapper in place. In isolated storage, two tasks were completed with `{"value":42}`; the one without a foreground child exposed that object, while the one whose child settled afterward exposed `{"status":"completed","result":{"value":42}}`. Keep the terminal outcome contract consistent regardless of whether completion waited for owned work.
41. **Raw commits can consume a generation input without admitting it to the transcript.** `crates/glass-core/src/durable.rs:478-512,549-558`; `crates/glass-core/src/durable_runtime.rs:628-649`: normal admission writes the input records, changes the checkpoint to `executing`, and consumes the input in one commit. The public commit path also accepts an update to `running`/`executing` followed by `submission.consume` without any transcript entry. In isolated storage this left the task's input null and its transcript empty; after restart the task was pending with checkpoint `executing`, still without the input in its active transcript. Enforce the admission invariant in the authoritative commit path or prevent external callers from applying internal admission transitions independently.
42. **Closing a Python subprocess client leaves its pipe descriptors open.** `clients/python/glass_client.py:447-460,1179-1192`: the subprocess close branch terminates and waits for the child but does not close the owned stdin and stdout streams. In a local probe holding five closed clients, the process retained ten extra descriptors and all ten streams reported `closed == False`; explicitly closing those streams restored the original descriptor count. Close owned streams in both subprocess and socket paths, including when termination or waiting fails.
43. **The Python client accepts an unterminated newline-delimited response.** `clients/python/glass_client.py:1211-1216,1242-1247`; `clients/python/README.md:69-70`: the newline-framed path parses bytes returned by `readline` at EOF without checking that a newline was received. A direct parser probe accepted a valid JSON-RPC response with no trailing newline exactly as it accepted the terminated response. Reject an incomplete EOF frame instead of treating it as a complete message.
44. **Aborting can replace an already-decided completion outcome.** `crates/glass-core/src/durable.rs:257-283,492-496,530-547,635-638`: `task.update` rejects changes to a `completing` task because its outcome is already decided, but `task.abort` can still overwrite that outcome. In isolated storage, a parent marked completed with a foreground child entered `completing` with a completed outcome; aborting it cancelled the child and left the parent `aborted` with an aborted outcome. Define whether cancellation can reverse a completion decision, and make the transition and observable result consistent with that contract.
45. **The documented workspace event cursor skips retained events on a limited page.** `crates/glass-dev/src/daemon.rs:1513-1537`; `docs/daemon.md:192-200`: the response's `newestSequence` is the newest event in the whole buffer, not the last event in the returned page, although the guide directs reconnecting clients to resume from it. Against a temporary daemon with retained events 1–4, a request with `limit: 1` returned event 1 and `newestSequence: 4`; resuming from 4 returned no events, skipping 2–4. Return and document a cursor for the last delivered event, distinct from the high-water mark. `operation.events` uses the same high-water-mark pattern at `crates/glass-dev/src/daemon.rs:1091-1118`; its pagination behavior has not been separately exercised.
46. **An owned conversation silently submits detached work after its owner finishes.** `crates/glass-core/src/durable.rs:320-323,596-630`; `crates/glass-core/src/durable_runtime.rs:192-215,497-533`: submission filters out an owner that is terminal or aborting rather than rejecting or explicitly reporting a change in ownership. In isolated storage, a conversation created with `ownerTaskId` retained that association, but a generation submitted after the owner completed had `owner: null` and remained pending independently. Define whether continued work is allowed after the owner settles; if detachment is intended, make it explicit to callers and observable in the submission contract.

## Additional frontend race — reproduced and fixed

- **Cross-conversation frontend event race.** A delayed history response suspended an event batch from one conversation; after switching conversations, a later `turn_start` event from that batch briefly inserted the previous conversation's message into the current timeline. Reproduced in Chromium with an isolated host fixture. Commit `be431605` guards the batch after asynchronous events and prevents stale follow/error callbacks from affecting the new view.

## Invariants addressed

- Explicitly model lifecycle transitions, pending/indeterminate outcomes, and ownership where the listed operations cross async or process boundaries.
- Reject conflicting idempotency reuse and new work after shutdown admission closes; every accepted operation remains inspectable or receives a terminal/indeterminate outcome.
- Recover the supported number of durable tasks without violating commit-size bounds or replaying uncertain effects.
- Make ownership and completion transitions explicit, including whether a completing task can receive new children.
- Preserve or explicitly reconcile decided outcomes and ownership when tasks are cancelled or their owners finish; make event pagination cursors advance only past delivered events.
- Preserve the correspondence between document schema versions and values across migration and forks; handle unresolved task dependencies explicitly.
- Preserve distinct tool-call occurrence identities and record typed execution outcomes independently of output text.
- Keep input consumption atomic with transcript admission and close client-owned transport resources on shutdown.
- Detect dependency cycles that combine explicit waits with foreground ownership, and keep task graphs and accepted transcript entries retrievable within protocol frame limits.
- Reject incomplete frames and uncorrelated tool requests before handing them to host code.
- Close or retain recoverable identity for partially initialized or unsuccessfully terminated remote sessions; do not report confirmed remote closure on error.
- Bound debugger transport shutdown when TCP peers or inherited stdio pipes remain open.
- Add deterministic regression coverage for the reproduced interleavings, boundaries, and failure paths. Preserve current protocol contracts and document any client concurrency contract.
- Prevent delayed frontend events from a previous conversation affecting the selected conversation.
