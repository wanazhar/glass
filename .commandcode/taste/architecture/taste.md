# Architecture & Design

- **Minimalism is the default**: ship the smallest thing that works and treat every added surface as permanent maintenance. Opened with "we ship minimal shit". Confidence: 0.85
- Strong skepticism that modern frontier models need many tools — proposed a bash-only tool surface unprompted. Prefer the smallest viable tool/API surface. Confidence: 0.8
- Binary size, resident memory, **and token cost per turn** are first-class design constraints, not afterthoughts. Expect them to be measured and reported at the end of a build. Cache hit rate and tokens-saved are treated as a named optimization objective to be quantified, not assumed: asked directly, "how to optimize cache hit and token saving while surviving compaction?". Confidence: 0.8
- Extensibility should be delegated to the user through config, skills, and mods rather than built into the core — ship the interface, not the features. But the interface must not be the weak point: "on mods yes we need to be as powerful as pi own. we need to become hackable too." Minimalism is a budget on *our* code, not a ceiling on what users can build — parity with the benchmark's extension surface is a requirement, not an optional extra. Confidence: 0.75
- **Optional, niche, or heavy capabilities ship as extensions disabled by default, not as core code.** Proposed it unprompted: "for the stuff u mention like prompt cache warmer, codemode etc, can we ship those as extensions? which is disabled by default." The default install must pay zero cost for anything it does not use. Confidence: 0.7
- **A feature you are told to build must still cost the core approximately nothing.** Asked how to support AGENTS.md/CLAUDE.md "without maxxing our lightweight stuff" — the accepted answer was pure prompt text under hard caps, or delegation to an out-of-process extension, so the binary and RSS stay flat. Required features do not get an exemption from the size budget. Confidence: 0.7
- **No originality tax**: when a proven implementation exists, borrow its design rather than reinventing it ("we can borrow pi features if u want"). Adopting a rival's proven pattern counts as a feature, not a compromise — but pair it with an honest note on where the copy is strictly worse than the original. Confidence: 0.7
- Prefers dependency-light implementations; a heavy runtime or framework is an immediate reject. Confidence: 0.7
- Native TUI/CLI is a hard requirement — no GUI, no web wrapper. Confidence: 0.75
- Wants one codebase reaching all frontier model providers (a base URL + model id) rather than per-provider forks. Confidence: 0.65
- Comfortable shipping without permission/safety gating in a single-user local tool, preferring to document the risk instead of gate it. Confidence: 0.5
- **The user reasons in a two-bucket triage: core vs. extension.** Their own framing for new work is "what else can we ship as core or as mods/extensions", so every proposal should arrive pre-classified into one of the two, with the core/extension call made explicitly rather than left implicit. Confidence: 0.8
- **The core/extension line is now settled, not an open question: the core stays at two tools and edit-style tools ship as opt-in mods/extensions.** When the question was put explicitly ("two tools and push capability into extensions, or three tools?"), the ruling was "2 core tools only. edit tools ship as mods". Do not re-propose a third core tool; a better edit mechanism is an extension, and its case is made in the extension's own README, not by growing the core. Confidence: 0.9
- **Add new behavior at the single choke point every code path funnels through, not at a call site.** Caught a real bug where post-write verification was attached to the inline bash call site, so it ran on one path and silently never on the pumped path — the unit tests passed because they exercised only one. When a path is duplicated, the fix is to consolidate into one function rather than remember to patch both. Corollary for guards: check them at the *dispatch* point, not inside the execution function — a second execution path (a worker thread, a pumped variant) will bypass anything the dispatcher does not check. Confidence: 0.8
- **Index an append-only log by absolute log position, never by projection length.** Compaction rewrites the model-facing projection in place while the log keeps appending, so the two lengths diverge permanently after the first compaction — a projection-relative index then points at the wrong slice of the log. Track `log_len` separately from `records.len()`. Confidence: 0.7
- **A decoder iterator over chunked network reads must buffer decoded events in an outbox.** One TCP read regularly carries several SSE events; returning the first emittable event drops the rest — which is how `message_delta`, and therefore every usage report, was silently lost on every response. Confidence: 0.7
- **A net-spend feature is not automatically a delete — if it buys a real secondary benefit, offer it disabled by default and let the user rule.** The cache-warmer was removed on economics, but the user's challenge surfaced two corrections: (1) the original "pays off with 2+ immediate turns" math was itself wrong — warming is +0.35P whether or not more turns follow, because any real turn already re-warms the cache, so it *never* pays; (2) it does buy latency (~1-2s faster time-to-first-token on a 100k prefix), a legitimate cost-for-latency trade. Outright deletion was the too-glib call; the honest move is to re-add it as a disabled-by-default extension with the net-spend stated and ask the user to confirm the trade. Confidence: 0.6
- **Model cache features against the real turn cadence of a coding session, not single-turn economics.** Turns land seconds apart — well inside the 5-minute cache TTL — so real work keeps the cache hot by itself; the only expiry case is an idle gap >5min. A warmer's sole viable case is exactly that gap, where it is net spend. The genuine long-horizon cache problem is compaction invalidating the message cache, not cold caches — fix that (system+tools breakpoint survives compaction, verbatim tail, append-only log) rather than warming. Confidence: 0.7
