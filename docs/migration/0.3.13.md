# Migrate from 0.3.12 to 0.3.13

Status: Historical migration guide for version `0.3.13` dated 2026-08-27. The
0.3.13 release record remains immutable; use the current 0.3.14 guide for the
active source and package contract.

Glass 0.3.13 keeps the 0.3.12 workspace, trust, revision, browser-target,
and resident-agent boundaries while making the coding workspace, editor
review, live browser presentation, and Pi SDK pin consistent across the
product.

## 1. Choose one package owner

The complete product is owned by `glass-dev` and provides the `glass` and
`glass-browser` executables. Install it at the exact matching version:

```console
cargo install glass-dev --version 0.3.13 --locked --force
```

The focused browser product and library are owned by `glass-browser`:

```console
cargo uninstall glass-dev
cargo install glass-browser --version 0.3.13 --locked --force
```

Do not install both package owners into one Cargo home: they share the
`glass-browser` executable name and the second install takes ownership of the
same binary. Library users should select the matching crate:

```toml
glass-browser = "0.3.13"
```

The `glass-dev` package carries the exact dependency `glass-browser =0.3.13`.
If you maintain a workspace checkout, update both package references together;
do not mix a 0.3.12 browser crate with the 0.3.13 development suite.

## 2. Refresh the managed Pi runtime

The managed native Pi AgentSession SDK is pinned to `0.84.3` for this source
line. Glass does not select an arbitrary newest upstream SDK. Check the local
prerequisites and readiness first:

```console
glass agent doctor
glass agent status
```

Node.js must be `22.19.0` or newer. Setup installs the managed runtime under
the platform local-data directory and records its selected runtime; it does
not run implicitly during Glass startup:

```console
glass agent setup
glass agent setup --update
glass agent setup --login
```

Use `setup --update` to replace an older managed SDK with the exact `0.84.3`
pin. Use `setup --login` to open the selected Pi CLI with the chosen agent
directory, complete Pi `/login`, and exit Pi. Alternatively, an existing
installation can be selected explicitly:

```console
glass agent setup \
  --sdk-entry /path/to/dist/index.js \
  --agent-dir /path/to/pi/agent
```

Authentication remains provider-owned. A missing or expired provider
credential leaves Pi unavailable while project, editor, and browser features
remain usable. Preserve `.glass/pi-sessions` when upgrading; sessions are not
silently rewritten when empty, outside the selected directory, or incompatible
with the selected SDK. Start a new session when the old file cannot be resumed.

## 3. Use the coding-workspace TUI

Start `glass` from the project root. The Agent landing surface now places
repository changes and checks beside the conversation, while the App surface
is the explicit browser-work area. The complete in-TUI entry point exposes
trust, readiness, setup/login, composer, files, PTYs, tests, LSP, Git, tasks,
and browser controls without a separate daemon bootstrap. Use `:actions` and
surface command menus to discover routes; `glass harness` lists or launches
installed harnesses, and bounded delegation is available through
`glass agent delegate` or `:harness delegate`.

In the Code surface, the editor and diff renderer now use the path to choose
syntax highlighting. Markdown fences and Mermaid source receive dedicated
handling, common language/path aliases are recognized, and a deterministic
plain-text/manual path remains available. Long lines wrap inside the pane
while preserving syntax, selection styling, and the visual cursor, including
at end of line.

Editor review state is actor-attributed and revision-aware. The following
commands are available from the Code surface:

```text
editor comment PATH START END TEXT
editor comment-selection TEXT
editor propose PATH SUMMARY TEXT
editor proposals
editor checkpoint NAME
```

Comments can be resolved. Proposals retain their base content and revision and
become stale rather than overwriting a changed buffer; checkpoints are named
in-memory states for deliberate review. Treat accepted changes as ordinary
reviewed mutations and re-read the current buffer before proposing another
replacement.

## 4. Use live browser presentation explicitly

The browser target picker, redacted target inventory, headed persistent
profiles, and disposable `--incognito --headless` mode remain available from
0.3.12. In 0.3.13, live browser presentation additionally supports Kitty
terminal graphics alongside Herdr and ANSI half-block output:

```console
glass --tui-live on \
  --tui-live-backend auto \
  --tui-live-quality balanced \
  --tui-live-fit contain
```

`--tui-live` is off by default. Select `auto`, `herdr`, `kitty`, or `ansi` as
the backend and use the bounded `data`, `balanced`, or `smooth` quality
profiles. ANSI fitting supports `contain`, `cover`, and `actual`. When live
pixels are disabled or unavailable, semantic browser output remains the
recovery path. Browser actions still require a selected, revision-matching
target and explicit confirmation where policy requires it.

## 5. Compatibility notes

There are no intentional Rust, CLI, MCP, or workspace-storage removals in this
migration. Continue using negotiated `glass.*` tools, current workspace
generations, and revision-bound browser actions. The one-way package boundary
and one-owner-per-Cargo-home rule remain important for clean upgrades.

The native resident path uses Glass's managed Pi AgentSession runtime. The
one-shot `glass agent prompt --harness pi` compatibility adapter remains a
separate CLI path; it does not imply resident-session ownership. TypeScript and
Python remain repository clients rather than npm or PyPI artifacts. When
embedding them from a checkout, keep their source version and handshake
metadata aligned with 0.3.13.

## 6. Roll back safely

If the new package or managed runtime cannot be used, preserve diagnostics and
session data before changing ownership. Remove the currently installed owner,
then install the previous package version as one coherent product:

```console
cargo uninstall glass-dev       # if glass-dev owns this Cargo home
cargo install glass-dev --version 0.3.12 --locked --force
```

For a focused browser installation instead:

```console
cargo uninstall glass-browser
cargo install glass-browser --version 0.3.12 --locked --force
```

Do not install both owners together. Keep a copy of `.glass/pi-sessions` and
any project configuration before rollback. If a session was created or changed
under the 0.3.13 SDK, select a known-compatible persisted session or create a
new session after rollback; never hand-edit an incompatible Pi session file.
Reinstall the managed runtime required by the selected package and verify its
readiness before resuming agent work.

## 7. Verify the migration

Record actual output from each check in your operational change record rather
than inferring success from installation alone:

```console
glass --version
glass --help
glass agent doctor
glass agent status
glass agent models
```

Then exercise the changed paths in a trusted project:

1. Open the TUI and confirm the Agent landing surface, `:actions`, and Code
   surface are reachable.
2. Open a source file and a diff; check syntax fallback, a wrapped line,
   selection/cursor placement, and the editor comment/proposal/checkpoint
   commands.
3. Start or attach the browser from App, inspect the redacted target picker,
   and choose semantic output when live graphics are unavailable. If a Kitty,
   Herdr, or ANSI backend is selected, record the selected backend and quality
   profile.
4. Run `glass agent setup --update` only when refreshing the managed runtime,
   then confirm readiness and a provider-free session startup before making a
   paid model request.
5. Confirm that the package owner remains singular and that the installed
   version reports `0.3.13`.

For a source checkout, retain the exact command output and source revision with
the release record. Do not describe external CI, signatures, registry state,
GitHub state, native certification, or fuzz coverage unless the corresponding
exact-source record is available in [release evidence](../release-evidence.md).
