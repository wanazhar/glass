# Verified form task execution boundary

## objective

Implement the first browser-backed Task Protocol execution path for the
`form.inspect`, `form.fill`, `form.validate`, and `form.submit` task families.
A validated authored task and compiled plan must execute through the existing
guarded semantic runtime, enforce the source revision and task limits before
mutation, preserve risk and confirmation requirements, and return explicit
verification or indeterminate-outcome state.

The first delivery is intentionally limited to forms. Navigation, tables,
collections, dialogs, and pagination remain browser-free plan operations until
their own execution contracts exist.

## context

Read these sources before implementation:

- `https://github.com/wanazhar/glass/issues/30` — Semantic Execution Engine
  product contract and the proposed `v0.2.7` verified-form milestone.
- `docs/architecture/automation.md` — bounded targeting, action, verification,
  and recovery rules.
- `docs/intent-resolution.md` — candidate resolution, confidence, policy, and
  guarded semantic execution.
- `docs/workflows.md` — workflow budgets, postconditions, retries, and outcome
  states.
- `src/task_protocol.rs` — authored task, limits, risk, revision, and
  postcondition contracts.
- `src/task_compiler.rs` — deterministic plan and plan-validation contract.
- `src/browser/session/intent.rs` — semantic resolution and execution boundary.
- `src/browser/session/fill.rs` — bounded multi-field form filling.
- `src/browser/session/workflow.rs` — guarded execution and verification.

## path

Expected implementation paths:

- `src/task_compiler.rs` or a focused task-runtime module for the validated
  plan-to-runtime boundary;
- `src/browser/session/` for form execution integration only where existing
  APIs cannot express the contract;
- `src/protocol.rs` and `src/mcp/` for typed request/result exposure if the
  boundary is made public in this increment;
- `src/cli/` only if a browser-backed task command is part of the same
  end-to-end path;
- focused unit, protocol, and fixture-backed integration tests.

Do not modify unrelated browser actions, non-form task families, release
publication workflows, or package distribution surfaces.

## contract

- Compilation remains browser-free and must not serialize input values.
- Execution must validate the plan before browser mutation.
- Form field resolution must be unique, evidence-backed, and scoped; no CSS
  selector, XPath, CDP node ID, or guessed target may enter the public task
  contract.
- The expected revision and declared action/time bounds must be enforced.
- `form.fill` must not submit unless the authored task requests submission.
- `form.validate` and submit flows must expose validation failures explicitly.
- Risky or ambiguity-gated tasks require confirmation before mutation.
- A post-dispatch verification failure is indeterminate when mutation may have
  occurred; it must not be reported as a safe retry.
- The execution result must preserve task kind, source revision, bounded step
  outcomes, verification state, mutation possibility, and retry guidance.
- Unsupported task families fail explicitly rather than being silently routed
  through a form path.

## verification

- Unit tests reject stale revisions, missing confirmation, over-budget plans,
  ambiguous form targets, unsupported task families, and unverified mutation
  outcomes.
- Form fixture tests cover inspect, fill, validation failure, explicit submit,
  and expected transition verification.
- Protocol tests round-trip successful and typed preflight/verification errors
  without serializing input values.
- The end-to-end test executes a supported form task through the existing
  guarded runtime and proves that no browser mutation occurs on preflight
  failure.
- Run focused tests, `cargo fmt --all -- --check`, Clippy with warnings denied,
  and the relevant documentation and fixture validators before marking this
  task done.
