## Finding

### P2 — blocking: invalid JSON-RPC notifications can ready or cancel the server

The main loop handles `notifications/cancelled` and
`notifications/initialized` before the shared request path validates
`request.jsonrpc == "2.0"` (`src/mcp/server.rs:227-229`, `255-259`). Envelope
validation currently occurs only in `initialize_response` and
`handle_request` (`src/mcp/server.rs:409-430`, `441-455`), neither of which is
called for those notification fast paths.

Consequently, after a valid initialize response, this invalid message:

```json
{"jsonrpc":"1.0","method":"notifications/initialized"}
```

transitions `Negotiated` to `Ready`, allowing browser operations without a
valid MCP initialized notification. Likewise, a cancellation notification with
an invalid or empty `jsonrpc` value can remove and fire an active request's
cancellation sender. Notification silence is correct, but silence must not mean
accepting invalid protocol messages as state-changing commands.

Validate the JSON-RPC envelope before every method-specific fast path. Invalid
notifications should remain silent and have no side effects. Add integration
coverage proving invalid-version initialized/cancelled notifications neither
transition lifecycle nor cancel an active request.

## Resolved review-01 findings

- Duplicate active numeric/string ids are now rejected under the cancellation
  map lock, so no sender is replaced (`src/mcp/server.rs:295-321`). The real MCP
  cancellation test also exercises duplicate rejection while a tool is active
  (`tests/browser_smoke.rs:235-254`).
- Tool failures now return only `browser tool failed`; target, selector,
  evaluated source, typed text, page, and CDP errors are not copied into the
  response (`src/mcp/server.rs:461-473`). Unit and real-browser sentinel tests
  cover invalid arguments and a private target (`src/mcp/server.rs:1052-1075`,
  `tests/browser_smoke.rs:277-294`).
- `RequestId` distinguishes absent from explicit null ids
  (`src/mcp/server.rs:26-77`). Notifications are suppressed across
  pre-initialization and overload paths, while null-id requests receive a null
  id response (`src/mcp/server.rs:218-293`; `tests/browser_smoke.rs:143-185`).
- Explicit `Uninitialized`, `Negotiated`, and `Ready` states now require the
  initialized notification before tools and reject repeat initialization
  (`src/mcp/server.rs:157-162`, `231-275`). The blocking finding above is the
  remaining validation edge in this otherwise-correct state model.
- The initial idle read is now documented as outside the partial-frame deadline
  (`docs/mcp.md:56-58`).
- Deterministic truncation, decimal-length, and byte sweeps supplement the fixed
  malformed-input corpus (`src/mcp/server.rs:1144-1173`). This is bounded
  property-style robustness coverage appropriate to the current task; a
  persistent coverage-guided fuzz target can remain release hardening work.
- Completion evidence now includes warm ping p50/p95 latency and request/
  response payload bytes, alongside binary/RSS deltas and an explicit
  allocator-measurement limitation (`docs/plan/tasks/mcp-008.md:70-77`).
