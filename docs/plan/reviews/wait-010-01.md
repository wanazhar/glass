# Review: wait-010 typed browser waits

Reviewed commit: `0fad62e` (`feat: add typed cancellable browser waits`)
against main `2fd91f7`.

Conclusion: **blocked**. The typed surface, polling cadence, bounded timeout
serialization, and basic MCP cancellation recovery are useful, but deadlines
do not bound condition evaluation, network quiet can report incorrect results,
and navigation was not actually moved onto the public wait engine.

## Findings

### P1 — blocking: explicit deadlines do not bound in-flight condition checks

`BrowserSession::wait` checks the deadline only after
`check_wait_condition(...).await` returns (`src/browser/session.rs:856-903`).
Every check can wait for the CDP client's independent 30-second command timeout;
a JavaScript predicate can return a never-resolving promise because evaluation
uses `awaitPromise: true` (`src/browser/cdp.rs:536-546`). A caller requesting a
100 ms wait can therefore block for roughly 30 seconds rather than receive its
100 ms `WaitTimeout`. Target resolution/state and page-info checks have the
same issue under a stalled CDP response.

Wrap each condition check in the remaining overall deadline. Timeout must drop
the pending CDP request through the existing pending guard and return the last
bounded state. Add a real test using a never-resolving JavaScript promise and a
short deadline, not only a predicate that immediately returns `false`.

The deadline inputs are also positive but not upper-bounded. MCP and CLI accept
`u64::MAX` milliseconds, and `started + deadline` can overflow `Instant` or
create a practically unbounded wait (`src/mcp/server.rs:616-620`, `776-785`;
`src/cli/args.rs:119-124`; `src/browser/session.rs:867-868`, `1010-1011`). Define
and enforce a maximum public deadline and network-quiet duration.

### P1 — blocking: lagged network events can produce false quiet

Network waits consume payload events from a broadcast channel with capacity
128. The loop handles only `Ok(event)` and silently ignores `RecvError::Lagged`
and channel closure (`src/browser/session.rs:1034-1059`). If a request-start
event is dropped but its finish is observed, the wait can declare quiet while
traffic is active; if a finish is dropped it can time out forever. This is
readily reachable below the advertised 1,024 request-ID bound because the
event channel is much smaller.

Treat lag as loss of correctness: fail with a bounded diagnostic or enter a
conservative overflow/unknown state that cannot report quiet. Align event
capacity and processing with the retained-request bound, and add a burst test
that forces receiver lag.

### P1 — blocking: Network domain ownership is not lease-safe

Each network wait independently sends `Network.enable`, and its guard sends
`Network.disable` on completion/drop (`src/browser/session.rs:996-1062`,
`1467-1493`). `BrowserSession` is callable concurrently by library users. If
two network waits overlap, the first completion disables events for the second.
Cancellation cleanup is spawned asynchronously, so it can also race a new wait
that has just enabled Network and disable the new scope. The MCP session mutex
serializes MCP tool calls but does not make the library contract safe.

Use a session-owned reference-counted Network lease: enable on the first
subscriber, disable after the last, and serialize cancellation cleanup with
new acquisition. The architecture explicitly requires diagnostic/domain
activation to follow subscription lifetime. Add overlapping wait and
cancel-then-immediate-reacquire tests.

### P1 — blocking: network quiet can miss already-active requests

The implementation subscribes, enables Network, then initializes an empty
in-flight set and starts its quiet clock (`src/browser/session.rs:1004-1014`).
CDP does not replay `requestWillBeSent` for requests that started before
`Network.enable`. A long-lived request already in progress is therefore
unknown, and the wait can succeed after the quiet interval even though the page
is not network-idle. The contract/documentation does not disclose that it means
“no requests observed after subscription.”

Either establish a reliable initial in-flight baseline or explicitly narrow
the condition semantics and name it accordingly. Add a test that starts a
delayed response before the wait begins. Redirect reuse while the bounded set
is full also over-increments `overflow_in_flight` for repeated starts with the
same untracked request id, leaving a phantom count after one finish
(`src/browser/session.rs:1039-1054`); bounded overflow tracking needs identity
or a conservative, documented overflow state.

### P2 — blocking: navigation does not use the typed wait machinery or caller deadline

`navigate` still has a separate `wait_for_page_event` implementation and a
hard-coded 20-second wait (`src/browser/session.rs:644-681`). It subscribes
before `Page.navigate`, which correctly avoids fast-load event races and the
redirect test is valuable, but it does not call `BrowserSession::wait`, expose
a deadline, poll current lifecycle state, or include the `Page.navigate` CDP
time inside one overall deadline. In the worst case navigation can spend the
CDP timeout plus the 20-second event wait.

This does not satisfy the task requirement to refactor navigation onto the same
wait machinery. Provide a deadline-aware navigation API that shares the
lifecycle engine, while keeping a documented compatibility default if needed.
Test fast load, redirect, timeout, and cancellation against the same total
deadline.

### P2 — blocking: documented exact-text wait is implemented as substring search

The public architecture calls `text=` an exact-text condition
(`docs/architecture/browser.md:89-94`), while the implementation returns true
for `text.contains(expected)` over the compact 16 KiB page text
(`src/browser/session.rs:924-927`, `692-699`). This is substring semantics and
can silently match “Not Ready” for `text=Ready`; content beyond the compact cap
can never match. Define whether the wait is exact page text, exact normalized
element text, or substring, name it accordingly, and make CLI/MCP docs and
tests agree. Reusing the deterministic `text=` locator semantics would avoid a
second incompatible definition.

### P2 — non-blocking: timeout state is lost when a condition check errors

Only expiry between successful checks creates `WaitTimeout`. Ambiguous targets,
temporarily detached references, non-boolean JavaScript, evaluation errors, and
event-stream closure return generic errors immediately without the typed
condition/deadline/last-state diagnostic (`src/browser/session.rs:873-903`,
`928-963`). Some are valid terminal errors, but transient target/page errors
need an explicit policy. Document which errors abort versus remain observable
last state; keep all agent-facing failure structures bounded and typed.

### P2 — non-blocking: condition arguments have no field-level size bound

URL, target, text, and JavaScript strings are retained directly from a request
up to the 4 MiB MCP frame maximum (`src/browser/session.rs:1524-1579`). This
conflicts with the architecture rule that every retained text field has an
explicit bound and makes repeated polling of a multi-megabyte predicate costly.
Add per-condition byte limits with UTF-8-safe validation before starting a
browser or wait.

### P3 — non-blocking: verification does not cover most typed conditions

Real-Chrome coverage exercises URL-prefix, text substring, target-stable,
immediate-false JavaScript, and network quiet. Lifecycle, exact URL,
target-attached, visible, hidden, enabled, non-boolean JavaScript, short-deadline
stalled checks, network lag/overlap/preexisting traffic, and navigation timeout
are not exercised (`tests/browser_smoke.rs:763-852`). The parser unit test only
constructs three variants. The task and architecture require deterministic
contract tests for every condition outcome, so this matrix should be completed.

### P3 — non-blocking: resource evidence is incomplete

The completion records `js=true` p50/p95, binary size, compact context, and
post-workload RSS (`docs/plan/tasks/wait-010.md:65-71`). It does not report
network-wait payload/event cost, peak workflow RSS, CDP round trips, or
deadline/cancellation overhead, despite architecture requiring peak memory,
payload size, and feature-path evidence. The published gates appear to pass,
but the evidence should distinguish cheap semantic polling from the explicitly
expensive Network scope.

## Positive observations

- Wait variants are typed internally and CLI/MCP share one string parser and a
  positive default deadline (`src/browser/session.rs:251-279`, `1524-1579`;
  `src/cli/runner.rs:114-127`; `src/mcp/server.rs:567-578`).
- The semantic loop subscribes before its first check, uses Page/DOM events for
  prompt wakeups, and retains a bounded 50 ms polling fallback
  (`src/browser/session.rs:856-903`). No sleeps were added to click/action paths.
- Timeout serialization caps last state to 512 UTF-8-safe bytes and does not
  echo raw condition arguments (`src/browser/session.rs:273-279`, `1581-1583`;
  `src/mcp/server.rs:483-498`).
- MCP cancellation drops the active wait through the existing request task and
  a real-browser integration confirms the serialized session remains usable
  afterward (`tests/browser_smoke.rs:324-347`).
- Network request IDs are locally bounded to 1,024 and successful waits disable
  Network before returning (`src/browser/session.rs:34-37`, `1004-1023`).
