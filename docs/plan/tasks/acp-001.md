## Objective

`glass-core acp`: an Agent Client Protocol (v1, agentclientprotocol.com)
server over stdio so editors (Zed and friends) can drive glass-core as their
agent subprocess. Ported from the ACP support in Cline, Codex's adapter,
Droid, Gemini CLI, and Copilot CLI (research/harness-features-2026.md).

## Context

- The protocol was pinned from the published v1 spec pages at implementation
  time: `initialize` response carries `protocolVersion`, `agentCapabilities`,
  `agentInfo`, `authMethods`; sessions are created with an absolute `cwd`;
  prompts stream as `session/update` notifications (`agent_message_chunk`,
  `agent_thought_chunk`, `tool_call` / `tool_call_update`, `usage_update`);
  `session/cancel` must end the turn with the `cancelled` stop reason, never
  an error.
- Reuses the headless engine wholesale: same tools, extensions, compaction,
  budgets, trust gate, and sandbox state. One glass session per ACP session,
  workspace bound to the client's `cwd`.
- Cancellation rides the existing steer path (an empty steer stops before the
  next command and kills owned process groups); the stream worker keeps the
  turn loop polling so a cancel lands while the provider is stalled.
- Deliberately unadvertised and answered `-32601`: `session/load`, `logout`,
  `session/set_mode`, and the client-side `fs/*`/`terminal/*` capabilities —
  glass runs its own filesystem and shell, and has no permission prompts by
  design. Client-supplied MCP servers are accepted and ignored (use the
  mcp-bridge extension host-side).
- `Progress` carries no provider call ids, so tool-call ids are synthesized
  and paired FIFO; updates are informational for the client.

## Paths

- `crates/glass/src/acp.rs` (new): JSON-RPC loop, reader thread, session
  registry, progress → update mapping, prompt-text folding, stop reasons,
  tests.
- `crates/glass/src/main.rs`: `mod acp`, `cu acp` dispatch, `make_provider`
  made `pub(crate)`, help text.
- `scripts/smoke-acp.py`: scripted client over pipes against the mock endpoint.
