# Workspace foundation review

- **Task:** `workspace-031-001`
- **Conclusion:** **BLOCKED**

This review compares the committed implementation with `docs/plan/tasks/workspace-031-001.md`, `docs/plan/analysis/release-031.md`, the issue #31 workspace and Glass Experience Layer amendments, `docs/architecture/README.md`, `docs/daemon.md`, and `docs/knowledge.md`. The changed implementation files and `tests/workspace_contract.rs` were read in full. No implementation files were changed.

## Findings

### [P1][blocking] Revoke a holder's lease when its attachment disconnects

**Location:** `src/workspace.rs:566-568` (with lease wrappers at `571-581`).

`disconnect` removes the attachment but does not change `lease_authority`. If that attachment held the lease, the state remains `Held` with a holder that can no longer be looked up: the former holder cannot call `release_lease` because it is now an `UnknownAttachment`, while an ordinary replacement attachment receives `AlreadyHeld`. Only another attachment with takeover capability can recover the workspace, so a disconnected client can leave mutation permanently unavailable. This conflicts with the daemon disconnect contract (release after active requests finish) and the workspace takeover/release requirements. Disconnect must revoke/release the holder atomically (after any tracked active requests) and advance the revision without closing the workspace.

### [P1][blocking] Reject lease mutations after the workspace starts closing

**Location:** `src/workspace.rs:545-561` and `571-581`.

The wrappers for `acquire_lease`, `takeover_lease`, and `release_lease` never inspect `self.lifecycle`. A caller can transition a workspace through `Closing` to `Closed` while an attachment remains, then acquire a fresh mutation lease from the closed workspace; `attach` also permits new attachments during `Closing`. A `Closed` lifecycle therefore does not stop mutation authority, and close can leave an active lease behind. Gate attachment/lease operations by lifecycle and revoke or otherwise finalize authority during close.

### [P1][blocking] Bind attachments to the workspace/profile scope

**Location:** `src/workspace.rs:399-404` and `556-560`.

`Attachment` carries only an ID, actor ID, role, and capabilities; it has no `WorkspaceScope`, and `Workspace::attach` performs no scope or ownership binding. The same attachment value (including its mutation/takeover capabilities) can consequently be attached to unrelated workspaces and acquire a lease in each one. This is an API-level cross-workspace attachment path, contrary to the issue #31 requirement that external attachments be temporary, scoped, revocable, and visible and that profile state not leak between workspaces. Bind an attachment to the workspace/profile (and validate it on attach) rather than treating an ID as globally reusable.

### [P1][blocking] Preserve profile scope in every resource-reference invariant

**Location:** `src/workspace.rs:230-232` and `283-292`.

The public fields and derived `Deserialize` allow a reference with `scope.profile_id = p1` and `resource = Profile(p2)`, even though `ResourceReference::profile` rejects that mismatch. `Display` then emits `glass://workspace/<w>/profile/p2`, dropping the stored `p1` scope, and parsing the emitted URI resolves to profile `p2`. A serialized or directly constructed value can therefore silently change profile when copied or round-tripped. Make the fields private and validate this pairing in constructors and deserialization (including workspace resources with an invalid profile scope).

### [P1][blocking] Encode ephemeral lifetime in resource references

**Location:** `src/workspace.rs:191-194` and `230-232`.

`WorkspaceScope` contains only `workspace_id` and an optional `profile_id`; it does not carry `WorkspaceStorage`, a generation, or any lifetime marker. Thus an ephemeral workspace and a durable workspace using the same ID produce indistinguishable `glass://workspace/<id>/...` references, and an old ephemeral reference can resolve to a later workspace after the ID is reused. The issue #31 addressability contract explicitly requires ephemeral references to identify their lifetime. Add a non-reusable generation/lifetime component (or an explicit ephemeral scope) to the reference and validate it at resolution.

### [P1][blocking] Enforce the alias bound before materializing and deserializing aliases

**Location:** `src/workspace.rs:104-112`.

`WorkspaceIdentity::new` collects the entire caller iterator before checking `MAX_ALIASES`, so an oversized (or non-terminating) iterator can allocate without the declared bound. The public `aliases` field and derived `Deserialize` also permit a caller or input snapshot to install more than `MAX_ALIASES`; only `add_alias` enforces the limit. This makes the advertised bounded identity state bypassable. Use a bounded/private collection and custom construction/deserialization that rejects as soon as the limit is exceeded.

### [P1][blocking] Enforce the attachment bound on every workspace construction path

**Location:** `src/workspace.rs:533-536` and `556-560`.

`MAX_ATTACHMENTS` is checked only by `Workspace::attach`. `Workspace` derives `Deserialize` while exposing its `attachments` map, so a snapshot can contain any number of attachments and deserialize successfully, bypassing the limit. The resulting workspace has unbounded attachment state and can exceed the resource bound even though the normal attach path rejects it. Keep the map private and validate its size in a custom deserializer (and on every replacement path).

### [P2][blocking] Validate profile, privacy, and storage combinations

**Location:** `src/workspace.rs:168-182` and `539-542`.

`WorkspaceConfig` is publicly constructible/deserializable without validation: for example, `ProfileMode::Named` with no `profile_id`, `ProfileMode::Incognito` with durable storage, or `PrivacyMode::Private` with durable storage are accepted. `Workspace::new` accepts these values and `scope()` merely copies the optional profile ID, so a named workspace can have no profile scope and a private/incognito workspace can be treated as durable by later profile/memory integrations. Provide one validating config constructor/deserializer and reject incompatible combinations before a workspace is created.

### [P2][blocking] Do not replace an attached identity while its lease is live

**Location:** `src/workspace.rs:556-560`.

`attach` inserts into the map even when the ID already exists. The lease authority records only that ID as holder, so attaching a different actor/role/capability set with the same ID silently changes the identity behind an existing lease without a revision bump: the new attachment may release or inherit the old lease, while replacing it with a non-mutating attachment can strand the lease. Reject duplicate IDs or explicitly revoke and revision-bump the old attachment/lease before replacement.

## Verified behavior and test evidence

The implementation does normalize and bound individual ID/alias values, round-trip the tested profile workflow URI, compare workspace/profile scopes exactly, reject observers in the lease authority, enforce revision checks on acquire/takeover/release, and leave lifecycle `Active` when a non-owner disconnects. The focused test source in `tests/workspace_contract.rs` covers only the happy-path URI round trip, one workspace mismatch, observer acquisition, takeover stale revision, release, and availability; it does not exercise the failing paths above. Tests were not executed in this review-only pass, and no project-wide command was run.

## Verdict

**Blocked:** the committed contract has release-blocking scope/lifetime and lease-authority failures, plus bypasses for the declared bounded-state limits. It should not merge until the P1 findings are fixed and focused tests cover disconnect/close, profile/lifetime reference invariants, attachment scope/replacement, and deserialization bounds.
