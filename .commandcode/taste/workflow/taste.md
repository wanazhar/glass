# Workflow & Engineering

- **Research before recommending.** When a design decision depends on what other tools actually do, survey the field first and bring back data (real numbers, cited sources) rather than answering from memory. Confidence: 0.8
- Expects claims to be backed by **measurements**, not estimates: wants concrete binary size, RSS, and startup numbers reported, and compares against competitor baselines. Confidence: 0.8
- **Names a specific rival as the benchmark and scopes work as a gap analysis against it** ("pi is our benchmark. lets beat pi. what can we ship next?"). Rank proposed work against that rival; "where we already win, where we lag, what I'd skip" is the expected shape of the answer. Confidence: 0.7
- When a ranked proposal is accepted, the directive is "do all of those" — treat a green-light on a list as a full commitment to every item on it, executed to completion with tests and a commit each, not a quiet renegotiation over a subset. Confidence: 0.7
- Rust is the implementation language of choice. Confidence: 0.85
- Wants a **test suite as part of the deliverable** — every module shipped with unit tests, all green before calling it done. Confidence: 0.85
- Test the parts that fail silently. Real bugs found: process-group kill semantics, JSON number vs string args, write-only file handle reads, CRLF in a streaming parser, a provider-side cache minimum that returns no error at all when the cached prefix is too short (you simply pay full price and never learn why). Check documented silent-degradation thresholds, not just error paths. Confidence: 0.8
- Verify the whole thing actually runs end-to-end (pty-driven interactive test against a mock server), not just that it compiles. Confidence: 0.8
- Debug by **isolating a hypothesis into a minimal standalone probe** rather than reasoning about the real code, and A/B test the suspect variable. Confidence: 0.75
- **A serial-format bug is invisible to unit tests; assert the exact wire shape and log the real outbound request.** The OpenAI adapter was sending `[[{...}]]` instead of `[{...}]` for `tools`. Every unit test passed; only a live run against a mock endpoint revealed that the model had no tools and the agent was silently inert. For anything serialized onto the wire, add shape assertions (array not nested, entry count == tool count) and inspect the captured request body when behavior is off. Confidence: 0.85
- **When an end-to-end run misbehaves, suspect the test harness before the code.** Several long debugging stretches were spent on a mock whose branch conditions, hardcoded fixtures, and logging were the actual bug. Log the raw request keys/roles/tool names the mock receives, and re-derive mock values (hashes, anchors) from live state instead of hardcoding them. Confidence: 0.75
- Write timing/ordering assertions as a **bound with both numbers named** ("four 150ms calls overlapped take ~150ms; serialised would be ~600ms") — an inverted equality assertion silently passes when the feature works. Confidence: 0.7
- Zero-warning, clippy-clean builds are expected. Silence the lints by fixing the code, not by adding `allow`. Confidence: 0.7
- Commit working increments to git as soon as a layer is green, rather than one giant commit at the end. Confidence: 0.65
- **Commit granularity is milestone-scoped, not per-feature.** Facing a repo with a large pre-existing dirty tree, the user chose "one commit per wave" — bundling each wave's work together with the pending changes in the files it touches and accepting "fewer, bigger, messier" commits — over the recommended clean baseline commit and over leaving everything uncommitted. Group commits by logical milestone/wave; do not over-split per feature. Confidence: 0.5
- Values a written README that explains the *why* behind each decision with numbers, not just usage instructions. Confidence: 0.7
- **Keep scanning the competitive landscape proactively rather than waiting to be pointed at one target.** "pls study more open source harness" — the user expects a standing read of the field, and answers sourced from fresh external research rather than from the one benchmark already named. Confidence: 0.8
- **Fan out broad research to parallel subagents with hard instructions, then personally re-verify the load-bearing claims before acting on them.** The prompts specified primary sources, cite-URLs, and mark-everything-unverified-as-UNVERIFIED, plus a fixed per-target report schema and explicit synthesis questions. Two of four agents errored; the two that returned were not trusted until the claims were re-checked against the arXiv paper and the repo directly — which is what surfaced that the benchmark had moved and that the project's own tool results were missing exit codes. Confidence: 0.8
- **Re-verify your own previously-quoted baseline numbers instead of carrying them forward.** Figures cited earlier in a project go stale; the competitor benchmark was found to have relocated, forked, and to be far larger than first reported. Confidence: 0.75
- **Actively recommend what NOT to build, backed by evidence** — either published measurements showing it underperforms, or absence of any sign of day-to-day use. A ranked wishlist without a "deliberately skipped, and here's why" section is an incomplete answer. Confidence: 0.8
- **Research output is expected to land as a committed notes file**, not just a chat answer: `research/<topic>.md` with a per-provider/mechanism table, exact numbers, the invalidation rules, a ranked list of what to change, and a References section of URLs. Commit research on its own, separately from the code it motivates. Confidence: 0.8
- **Before proposing changes from research, audit the current implementation against it and measure the gap in our own units** (grep where the mechanism is wired, compute our actual prefix size, check it against every documented threshold, and report "N tokens short of the M minimum on which models"). Generic advice is not the deliverable; the delta against today's code is. Confidence: 0.8
- **Derive the cost model algebraically and quote the break-even point, rather than asserting that an optimization "is always cheaper".** Working the per-turn equation (cached vs uncached, solving for the crossover prefix size) produced the finding that inverted the standard advice, and turned a vague "optimize caching" request into a number the design can be checked against. Confidence: 0.8
- **Validate any hand-built simulation against a documented worked example before quoting its output.** Several rounds of writing and rewriting a cost simulator exposed accounting bugs in the model itself (double-counted writes, wrong sign on the break-even). Anchoring to the vendor's own turn-by-turn table is what made the numbers trustworthy; the intermediate outputs were wrong and would have been quoted. Confidence: 0.8
- **When a computed output contradicts itself, stop and re-derive the comparison logic before reporting it** (e.g. a "TOO SHORT" verdict on a prefix that had just been found long enough). A cheap per-line trace of the inputs beats shipping a confidently inverted table. Confidence: 0.7
- **Keep the auto-managed taste/learning directory out of commits.** `.commandcode/` is owned by the learning system, not the project; unstage it (`git restore --staged .commandcode/`) before committing work. Confidence: 0.85
- **To drive the glass TUI in a pty test: type character-by-character with small delays, send `\r` (not `\n`) for Enter, and wait for the `❯` prompt glyph.** `>` is not the prompt, and a bare `\n` types the text without submitting — both cost debugging rounds before the real behavior was found. Confidence: 0.8
- **glass-core reads config from a file, not CLI flags — to point it at a mock, write `config.toml` under `$XDG_CONFIG_HOME/glass-core/` and set `XDG_CONFIG_HOME`/`XDG_DATA_HOME`.** CLI args are silently ignored, so wrong config means the binary hits the real provider API instead of the mock. Redirect config before any mock run. (Legacy pre-rename files under the `glass/` dirs are copied into the `glass-core/` dirs once on first run.) Confidence: 0.8
- **Extract pure request-body builders out of the network path so the wire shape is testable without a socket.** `stream()` needs a live connection, so bugs there were invisible to every unit test; a `build_body()` fn lets tests assert the exact JSON, and the tested path must be the same one `stream()` calls — otherwise the assertion guards a path that is not the shipped one. Confidence: 0.75
- **Never research, cite, or recommend aider.** The user ruled it legacy — "no one use this in 2026" — and called out that it surfaces in LLM answers only because of training-data density. Exclude it from field surveys and from subagent prompts explicitly ("do not research or mention aider"); an honest "no evidence found" beats a familiar-but-irrelevant citation. When the user flags a training-data bias, actively resist it instead of leaning on it. Confidence: 0.9
- **A "is this design correct?" question is answered by auditing the code and testing behavior, not by opining on the architecture.** Asked whether the TUI design was right, reading the editor and driving a real pty paste surfaced two bugs no design opinion would have caught: pasted text was silently dropped (an event match fell through to `continue` on `Event::Paste`), and multi-line rendering drew every row on top of each other. Confidence: 0.75
- **When re-adding a feature that was removed for defects, fix the root cause rather than restoring it as-was.** The cache-warmer's first version read a key the host never sent and could not have worked even with the key fixed — a subprocess holds no credentials and the host is idle exactly when warming must happen. The re-add declares policy in the extension and moves the mechanism into the host's background thread. Confidence: 0.7
- **When the user names a set of rival harnesses, the job is to mine each for its distinctive feature and implement those features** — "find features from pi, omp, codex, t3 codes, then implement". The deliverable is the implemented features (each verified end-to-end against a mock and committed separately, with README docs), not a survey or a gap analysis. Extract what makes each harness *different* (t3's `todo` plan tool, pi/omp/codex's subagents and `/model`), not their commonalities, and track one todo per named-harness feature until all are shipped. Confidence: 0.75
- **Validate terminal-rendering changes by replaying a real PTY capture through a VT100 emulator, and assert on the raw byte stream as ground truth.** Drive the release binary in a PTY against a mock SSE provider, capture the raw output, then replay it through a minimal VT100 emulator (handling CSI H/K/J, CR, LF, UTF-8) to see the actual final screen. The emulator's rendered screen is a convenience — it can have its own scroll bugs — so structural assertions (prompt echoed exactly once, chip before result, usage line present, ordering of markers) belong on the raw bytes. Built before the visual changes, this harness immediately caught that bash — the primary tool — rendered no chip at all (the pumped/parallel paths bypass the progress emits) and a missing `\x1b` escape that would have printed a literal `[31m`. Confidence: 0.8
- **When editing source containing literal `\x1b[...]` escape sequences, use a python heredoc with an exact unique-match assertion instead of the file-editing tool.** The edit tool's fuzzy match mangles escape sequences in parameters and has corrupted identifiers (`outcome.spill` → `spill`); a `python3 - <<'PYEOF'` script that asserts `src.count(old) == 1` and does a plain string replace applies the intended bytes exactly. Useful for any Rust source with ANSI styling, which this codebase is full of. Confidence: 0.75
- **When scoping a new feature, first grep for existing machinery to reuse.** Plan mode was scoped as "reusing the read-only detection we already have" from the concurrency classifier instead of writing fresh classification. Reuse beats a new implementation when the mechanism already exists in the codebase — check for it before designing. Confidence: 0.55
- **"Find more features to ship" delegates discovery, not just implementation.** Expected move: read the README and core modules, grep TODO/FIXME/unimplemented, check git log and uncommitted work, then return a ranked, sized proposal classified by fit with the project's philosophy — with a structured pick question, not an open "what do you want?". Feature candidates should be grounded in gaps the codebase itself reveals (unused machinery, invisible state, missing commands), not invented wholesale. Confidence: 0.55
- **Validate rendering at multiple terminal widths, not just the dev terminal's.** Parameterize the PTY driver and the VT emulator with rows/cols, then capture at a phone-sized narrow size (24x32 / 24x40) and a wide one (30x100) to prove the compact path triggers and the wide path doesn't regress. Measure each rendered line's true display width — strip ANSI escapes from the raw capture, count the chars, assert ≤ terminal width. This caught a truncation budget that reserved no column for the ellipsis, pushing a "40-col" line to 41. Confidence: 0.8
- **When a bug is only *felt* (display lag, slowness) and a local run cannot reproduce it, separate app behavior from transport behavior before changing code.** Build a timing/ordering probe that asserts the output for event N is emitted *before* event N+1 is sent — that proved the TUI was already per-key and moved the fix from the input loop to the presentation layer (atomic frames via synchronized output), instead of chasing a nonexistent input bug. Confidence: 0.75
- **Cargo's fingerprint can go stale in glass-core: `cargo build` (both profiles) reports "Finished" in ~0.1s and silently skips recompiling despite real source changes, leaving binaries that predate the code.** When a just-shipped feature "doesn't show" for the user, suspect the build before the code: force a rebuild (`touch` the changed sources), then confirm the feature actually landed in the binary (`strings target/{debug,release}/glass-core | grep <feature string>`) and in a live PTY run of the exact binary `cargo run` produces. Source state and cargo's "fresh" verdict are not evidence the binary has the change. Confidence: 0.8
- **Ship large feature batches as staged waves, each wave ending with the full verification gate — workspace tests, `clippy -D warnings`, release build, and the entire offline smoke-suite list — plus its own commit, and register new suites in CI.** "Same rhythm as last round" is the user's standing endorsement of this cadence: verify a wave completely, commit it, then start the next. Expect a fresh delta-focused landscape study to open each new round of "what to ship next". Confidence: 0.65
