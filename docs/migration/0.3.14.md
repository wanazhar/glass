# Migrate from 0.3.13 to 0.3.14

Status: Current migration guide for version `0.3.14` dated 2026-08-29. The
0.3.13 release record remains historical; this guide describes the 0.3.14
source and package contract.

Glass 0.3.14 keeps the 0.3.13 package, trust, revision, browser-target, and
resident-agent boundaries while making the coding workspace, editor, composer,
governed Git surface, and overnight crew evidence part of one native workflow.

## 1. Choose one package owner

The complete product is owned by `glass-dev` and provides the `glass` and
`glass-browser` executables. Install it at the exact matching version:

```console
cargo install glass-dev --version 0.3.14 --locked --force
```

The focused browser product and library are owned by `glass-browser`:

```console
cargo uninstall glass-dev
cargo install glass-browser --version 0.3.14 --locked --force
```

Do not install both package owners into one Cargo home: they share the
`glass-browser` executable name and the second install takes ownership of the
same binary. Library users should select the matching crate:

```toml
glass-browser = "0.3.14"
```

The `glass-dev` package carries the exact dependency `glass-browser =0.3.14`.
If you maintain a workspace checkout, update both package references together;
do not mix a 0.3.13 browser crate with the 0.3.14 development suite.

## 2. Start the resident coding workspace

Start `glass` from the project root. The Agent landing surface places the
conversation beside repository changes, checks, diagnostics, and browser
evidence. The shared composer is available from every surface:

```text
Ctrl-L   open the composer
Alt-A    open the composer from the editor
Ctrl-D   cycle Ask, Plan, and Agent modes
Enter    send the current draft
```

Ask and Plan are read-only for mutations. Agent changes are proposal-oriented;
review and prove them before accepting. Use `:actions` or `:` to discover
surface routes, and use `a` for the action menu when the footer exposes it.

## 3. Use the native editor and review state

The Code surface opens a modal editor with Normal, Insert, Select, and Agent
modes. It supports structural motions and text objects, soft wrapping,
syntax-aware source and diff rendering, same-textobject multi-cursor ranges,
local/resident FIM ghosts, pair-apply, and revision-aware cursor placement.
Tree-sitter updates incrementally when the language is supported; the lexical
fallback remains deterministic for unsupported paths.

The review commands retain actor and revision context:

```text
editor comment PATH START END TEXT
editor comment-selection TEXT
editor propose PATH SUMMARY TEXT
editor proposals
editor checkpoint NAME
```

Comments can be resolved. Proposals retain their base content and revision and
become stale rather than overwriting a changed buffer. Checkpoints are named
in-memory states for deliberate review. Re-read the current buffer before
accepting another replacement.

LSP diagnostics and inlay hints appear in the gutter when a real language
server is available. `K`, `gd`, `gr`, `go`, and `i` provide the documented
hover, definition, references, implementation, and inlay routes. `gm` adds
structural carets and `gn` moves to the next incomplete ghost identifier.

## 4. Use the workbenches and governed Git verbs

Git, Debug, Terminal, Tasks, and More are separate workbenches. Use their
action menus to inspect the current state before a mutation. The resident MCP
surface exposes these Git verbs:

```text
glass.git.fetch
glass.git.pull
glass.git.merge
glass.git.rebase
glass.git.stage
glass.git.unstage
glass.git.discard
glass.git.push
```

Fetch, pull, merge, rebase, discard, and push remain governed by workspace
trust, path confinement, actor attribution, current revision/branch state, and
confirmation policy. Git worktrees created by the workspace remain under
`.glass/worktrees`.

## 5. Queue and review an overnight crew

The Tasks surface and `glass.task.crew` can queue a bounded architect,
implementer/tester, reviewer, and browser-verification crew. Each implementer
works in an isolated worktree. A `before-crew:<goal>` checkpoint records the
starting revision, and the durable wake pack is stored under:

```text
.glass/crew/<crew-id>.json
.glass/crew/latest.json
```

Use `glass.task.wake` or the TUI `:task wake` route to refresh and inspect the
pack. Wake is read-only: it folds member state, changed files, tests,
verification, browser evidence, and acceptance proposals for human review. The
workspace-local Agent checklist is separate and remains at
`.glass/todos/session.json`.

## 6. Pi runtime and client compatibility

The resident path continues to use the managed native Pi AgentSession SDK
(`0.84.3`). Check readiness before making a provider request:

```console
glass agent doctor
glass agent status
glass agent models
```

The native setup, login, update, session selection, follow-up, branch, rewind,
and compaction routes remain explicit. Provider credentials and prompt content
are not included in replay or release evidence. TypeScript and Python clients
should keep their handshake metadata at `0.3.14` and use negotiated `glass.*`
tools; the full-product conformance fixture now contains 344 tools.

## 7. Roll back safely

Preserve diagnostics, project files, `.glass/pi-sessions`, and crew evidence
before changing package ownership. Remove the current owner and install the
previous coherent product:

```console
cargo uninstall glass-dev       # if glass-dev owns this Cargo home
cargo install glass-dev --version 0.3.13 --locked --force
```

For a focused browser installation instead:

```console
cargo uninstall glass-browser
cargo install glass-browser --version 0.3.13 --locked --force
```

Do not install both owners together. If a session, proposal, or workspace
record was created under the 0.3.14 SDK, select a known-compatible persisted
session or create a new one after rollback; never hand-edit an incompatible
Pi session file. Crew worktrees and wake files can be retained for review, but
do not accept a proposal after changing the source revision without re-reading
its base.

## 8. Verify the migration

Record actual output from each check in the operational change record:

```console
glass --version
glass --help
glass agent doctor
glass agent status
glass agent models
```

Then exercise the changed paths in a trusted project:

1. Open the TUI and confirm the Agent landing surface, shared composer, and
   Code, Git, Tasks, and More workbenches are reachable.
2. Open a source file and a diff; check syntax fallback, a wrapped line,
   structural selection, an FIM ghost, LSP gutter state, and a proposal
   checkpoint.
3. Inspect Git status and use a read-only action before trying a governed
   fetch, pull, merge, rebase, or push.
4. Queue or inspect a bounded crew only in a trusted project, then review its
   wake pack before accepting any proposal.
5. Start or attach the browser from App and use semantic output when live
   graphics are unavailable. Browser mutations still require current evidence.
6. Confirm that one package owner remains installed and that the version
   reports `0.3.14`.

For a source checkout, retain the exact command output and source revision with
the release record. Do not describe external CI, signatures, registry state,
GitHub state, native certification, or fuzz coverage unless the corresponding
exact-source record is available in [release evidence](../release-evidence.md).
