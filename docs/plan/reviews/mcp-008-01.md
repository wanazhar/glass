# Review: mcp-008 hardened MCP transport

Reviewed commit: `cc9e774` (`feat: harden MCP transport and cancellation`).

Conclusion: **blocked**. Framing limits, strict UTF-8 decoding, response bounds,
version checking, serialized browser access, and the CDP pending guard are good
foundations. Cancellation ownership, notification semantics, and error
redaction still violate task-level correctness and security requirements.

## Findings

### P1 — blocking: duplicate request IDs corrupt cancellation ownership

The cancellation map is keyed only by serialized JSON-RPC id, and accepting a
request unconditionally replaces any existing sender
(`src/mcp/server.rs:204-212`). If two active requests use the same id, the
second request makes the first uncancellable. Worse, when either task finishes,
it unconditionally removes that shared key (`src/mcp/server.rs:233-237`), which
can remove the other request's sender. A later cancellation can therefore
cancel neither operation or the wrong logical owner depending on timing.

This is especially relevant because up to eight requests are admitted and
queued behind the serialized session mutex. Reject a duplicate active id, or
store an ownership token and remove/cancel only when the token still matches.
Add race tests for duplicate numeric and string ids, completion in both orders,
and cancellation while one duplicate is queued. Until then cancellation is not
reliable under the advertised concurrency contract.

### P1 — blocking: tool errors echo secret-bearing arguments

`tools/call` converts every browser error directly to client-visible text
(`src/mcp/server.rs:352-360`). Browser errors include caller-controlled target
values, for example `element not found: {target}`, stale references, and
no-DOM-reference errors (`src/browser/session.rs:700-712`, `827-884`). A target
can contain private page text or a CSS selector carrying a secret. CDP and
page-authored errors may likewise contain evaluated or page-derived content.

This contradicts the requirement to keep secret-bearing metadata out of error
data (`docs/plan/tasks/mcp-008.md:37-38`) and the completion claim that errors
contain no tool arguments (`docs/plan/tasks/mcp-008.md:59-61`). Metadata-only
logging does not protect the response channel. Return bounded typed/sanitized
tool errors by default, retaining detailed causes only in explicitly safe local
diagnostics, and add tests using a sentinel secret in each sensitive argument.

### P2 — blocking: pre-initialization notifications receive responses

Only cancellation and `notifications/initialized` are suppressed before the
initialization gate. Any other notification (a request without an id) receives
`server is not initialized` (`src/mcp/server.rs:167-189`). An `initialize`
notification also receives an initialize response because it is handled before
the notification path (`src/mcp/server.rs:171-177`). JSON-RPC notifications
must not receive responses, including errors. The overload path has the same
problem for a ninth notification (`src/mcp/server.rs:192-201`).

Additionally, `Option<Value>` collapses an explicit `"id": null` and an absent
id, while response serialization omits `id` for `None`
(`src/mcp/server.rs:26-45`). Parse/invalid-request errors therefore omit the
required JSON-RPC null id, and an explicit null-id request is treated as a
notification. These behaviors can desynchronize strict clients and contradict
the documentation's claim of JSON-RPC operation. Represent id presence
separately, suppress every notification response on every fast path, and test
pre-init, initialize, overload, invalid-version, and malformed-request
notifications.

### P2 — blocking: initialization is a boolean, not the MCP lifecycle

A successful initialize response immediately sets `initialized = true`
(`src/mcp/server.rs:171-175`), so browser tools are accepted before the client
sends `notifications/initialized`. That notification is also silently accepted
before any initialize request (`src/mcp/server.rs:179-180`). Repeated initialize
requests are allowed; a later incompatible initialize does not clear the prior
initialized state. These transitions are not covered by the negotiation tests,
which call `initialize_response` in isolation.

Use explicit `Uninitialized`, `Initializing/Negotiated`, and `Ready` states;
allow normal operations only after the initialized notification; and reject
out-of-order or repeated lifecycle messages deterministically. Add a stdio
integration test for the complete state transition, not only incompatible
version followed by `tools/list`.

### P2 — non-blocking: framing timeout does not cover an idle initial read

`read_initial_line` awaits `fill_buf()` before entering the timeout
(`src/mcp/server.rs:697-707`). Thus the documented frame timeout begins only
after at least one byte arrives. This is reasonable for an idle stdio server,
but `FRAME_BODY_TIMEOUT` and the completion's unqualified input-timeout claim
do not make that scope clear. Document it as an inter-byte/in-progress-frame
deadline or wrap the first-byte wait as well if an absolute request deadline is
intended.

### P3 — non-blocking: the malformed-input corpus is a regression list, not fuzzing

The committed corpus has five fixed cases
(`tests/fixtures/mcp_framing_corpus.json:1-27`) and its test only checks whether
`read_message` returns `Ok` (`src/mcp/server.rs:1038-1047`). There is no property
generator or fuzz target for arbitrary truncation, huge decimal lengths,
header permutations, JSON nesting, or invalid UTF-8. This provides useful
regression coverage but does not satisfy the task's stated unit/property and
fuzz verification (`docs/plan/tasks/mcp-008.md:41-45`). Add a bounded property
test or persistent fuzz target and document its run command/corpus.

### P3 — non-blocking: resource evidence omits requested latency/payload data

The completion records binary, idle RSS, and workflow peak RSS
(`docs/plan/tasks/mcp-008.md:63-68`), but the architecture requires every new
feature to report steady-state RSS, peak allocation, p50/p95 latency, payload
size, and binary delta (`docs/architecture/automation.md:56-59`). Transport
latency and measured payload-bound behavior are not recorded. The hard release
budgets still pass, but the evidence should be completed or the architecture
should explicitly exempt safety-only transport changes.

## Positive observations

- Content lengths are parsed and rejected before body allocation; newline,
  header, body, response, concurrency, and outbound queue bounds are explicit
  (`src/mcp/server.rs:18-24`, `643-782`).
- Protocol bytes use strict UTF-8 conversion rather than lossy decoding
  (`src/mcp/server.rs:660-687`).
- Dropping a pending CDP send emits an actor cancellation, and actor ordering
  removes the response sender before a late response is processed
  (`src/browser/cdp.rs:86-115`, `255-293`).
- Tool arguments, raw ids, and cancellation reasons are absent from request
  logs (`src/mcp/server.rs:69-75`, `158-165`, `267-297`).
