# Narrow audit: wait-010 Network lease release

Reviewed branch through `3947047` (`fix: consume network leases exactly once`).

Conclusion: **blocked**. The prior double-decrement race is fixed after release
acquires the lease mutex, and CDP actor ordering is sound. Cancellation while
waiting to acquire that mutex can now leak the lease instead.

## Finding

### P1 — blocking: `disable` disarms before its lease is consumed

`NetworkDomainGuard::disable` sets `self.armed = false` and then awaits
`release_network_lease`, whose first operation is an async mutex acquisition
(`src/browser/session.rs:1520-1523`, `1539-1547`). If another enable/disable
transition holds that mutex across a CDP acknowledgement, this wait can block.
Cancellation in that interval drops an already-disarmed guard: `Drop` performs
no cleanup, but this guard's count was never decremented. The leaked count keeps
the Network domain logically leased indefinitely and prevents the eventual
last owner from disabling it.

Consume ownership only after acquiring transition ownership. One safe shape is:

1. await the lease mutex while the guard remains armed;
2. disarm the guard;
3. decrement exactly once under that held mutex; and
4. if it reached zero, enqueue/await `Network.disable` while retaining ordering.

Cancellation before step 1 then leaves the guard armed so `Drop` schedules
release; cancellation after step 2 cannot double-decrement because ownership
has been consumed. Add a deterministic test that holds the lease mutex in a
delayed transition, starts final `disable`, cancels it while queued for the
mutex, and verifies drop cleanup decrements and ultimately disables Network.

## Confirmed behavior

- Once `release_network_lease` owns the mutex, count decrement and queued
  `Network.disable` remain serialized against later acquisition
  (`src/browser/session.rs:1539-1548`).
- `CdpClient::send` enqueues its request before awaiting the response, and the
  actor processes commands in queue order (`src/browser/cdp.rs:255-293`,
  `160-184`). If a final disable command has been enqueued and its response
  future is then cancelled, a later enable acquired after mutex release follows
  that disable in actor order.
- Clearing `armed` before the release call prevents the previous
  disable-error/response-cancellation path from invoking a second decrement.
  The blocker is specifically cancellation before mutex acquisition.
- No unrelated wait, text, navigation, MCP, or pointer code changed in
  `3947047`.
