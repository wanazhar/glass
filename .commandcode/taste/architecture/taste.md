# Architecture & Design

- **Minimalism is the default**: ship the smallest thing that works and treat every added surface as permanent maintenance. Opened with "we ship minimal shit". Confidence: 0.85
- Strong skepticism that modern frontier models need many tools — proposed a bash-only tool surface unprompted. Prefer the smallest viable tool/API surface. Confidence: 0.8
- Binary size and resident memory are first-class design constraints, not afterthoughts. Expect them to be measured and reported at the end of a build. Confidence: 0.8
- Extensibility should be delegated to the user through config, skills, and mods rather than built into the core — ship the interface, not the features. But the interface must not be the weak point: "on mods yes we need to be as powerful as pi own. we need to become hackable too." Minimalism is a budget on *our* code, not a ceiling on what users can build — parity with the benchmark's extension surface is a requirement, not an optional extra. Confidence: 0.75
- **Optional, niche, or heavy capabilities ship as extensions disabled by default, not as core code.** Proposed it unprompted: "for the stuff u mention like prompt cache warmer, codemode etc, can we ship those as extensions? which is disabled by default." The default install must pay zero cost for anything it does not use. Confidence: 0.7
- **A feature you are told to build must still cost the core approximately nothing.** Asked how to support AGENTS.md/CLAUDE.md "without maxxing our lightweight stuff" — the accepted answer was pure prompt text under hard caps, or delegation to an out-of-process extension, so the binary and RSS stay flat. Required features do not get an exemption from the size budget. Confidence: 0.7
- **No originality tax**: when a proven implementation exists, borrow its design rather than reinventing it ("we can borrow pi features if u want"). Adopting a rival's proven pattern counts as a feature, not a compromise — but pair it with an honest note on where the copy is strictly worse than the original. Confidence: 0.7
- Prefers dependency-light implementations; a heavy runtime or framework is an immediate reject. Confidence: 0.7
- Native TUI/CLI is a hard requirement — no GUI, no web wrapper. Confidence: 0.75
- Wants one codebase reaching all frontier model providers (a base URL + model id) rather than per-provider forks. Confidence: 0.65
- Comfortable shipping without permission/safety gating in a single-user local tool, preferring to document the risk instead of gate it. Confidence: 0.5
- **The user reasons in a two-bucket triage: core vs. extension.** Their own framing for new work is "what else can we ship as core or as mods/extensions", so every proposal should arrive pre-classified into one of the two, with the core/extension call made explicitly rather than left implicit. Confidence: 0.8
- **Add new behavior at the single choke point every code path funnels through, not at a call site.** Caught a real bug where post-write verification was attached to the inline bash call site, so it ran on one path and silently never on the pumped path — the unit tests passed because they exercised only one. When a path is duplicated, the fix is to consolidate into one function rather than remember to patch both. Confidence: 0.8
