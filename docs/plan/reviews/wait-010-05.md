## Resolution

`NetworkDomainGuard::disable` now waits for the lease mutex while the guard is
still armed (`src/browser/session.rs:1520-1522`). Cancellation while queued for
that mutex therefore drops an armed guard, and `Drop` schedules the normal
lease release instead of leaking the count.

Once the mutex is acquired, `disable` clears `armed` and immediately passes the
held guard to `release_network_lease_locked` without an intervening await
(`src/browser/session.rs:1521-1523`, `1547-1555`). That function decrements the
count exactly once before its only cancellation point, the final
`Network.disable` acknowledgement. Cancellation or a CDP error after decrement
cannot trigger a second release because the guard is already disarmed.

The mutex remains held through the queued disable command. `CdpClient::send`
enqueues the command before awaiting its response, so any later acquisition
can enqueue `Network.enable` only after the earlier disable has entered actor
order. This preserves disable-then-enable ordering even if the disable response
future is cancelled.

Together these paths cover cancellation before lock acquisition, after lock
acquisition, during command acknowledgement, and ordinary success without
leak or double-decrement.
